# 学生端开发需求与技术方案

> 日期：2026-08-09  
> 状态：开发方案稿  
> 适用范围：学生端首版 / 单班 30+ 学生并发  
> 核心变化：ASR 与 TTS 全部本地部署；Dify 作为已存在的外部问答服务接入  
> GPU 条件：**2 × RTX 4090 48GB**  
> 视频原则：**形象素材预处理与 WebRTC 运行期解耦；Session 绑定创建时的形象版本，运行中不热切换**

## 首版管理端范围（已收敛）

管理端挂在学生端服务端，三块：

| 能力 | 做什么 |
|------|--------|
| **形象** | 上传 `avatar.mp4` → 转码/抽帧 → Avatar Package；滑块调 `idle/talk` |
| **音模** | 上传参考 wav + 提示文本 → 注册 `voice_id` |
| **智能体** | 登记 Dify API Key → `GET /v1/info` 取名称 → 供学生端/并发页选择 |

学生端与并发页：选形象 → 选音模 → 选智能体 → 再问答。  
改默认只影响之后新建 Session。素材开头一般为闭嘴待机，**不强制视频时长**（常见约数秒即可）。

## 1. 文档目的与硬性要求

本文统一将整套面向学生使用的数字人问答系统称为 **「学生端」**。学生端包含学生端 Web、学生端服务端、本地 ASR、本地 TTS、学生端 Publisher 与 WebRTC/SFU 链路。

本文在原业务方案基础上，落到可以直接开发、联调和压测的工程实现。

### 1.1 三项硬性要求

以下三项不是“优化项”，而是项目验收的最高约束。

#### 硬性要求 A：WebRTC 必须支持多路

系统目标为单班 **30+ 学生，每个学生一路独立 WebRTC Session / 学生端 Publisher**。

必须满足：

- 多个学生可以同时在线；
- 每个学生拥有独立的视频轨和音频轨；
- 单个学生的录音、ASR、Dify、TTS、视频状态不能串到其他学生；
- 学生端 Publisher、Session、音频缓冲、TTS Job 都必须按 `session_id` 隔离；
- 禁止使用“全系统只有一个全局播放器/全局 TTS/全局视频状态”的实现；
- 单路异常不能导致其他 WebRTC Session 停止。

首版以 LiveKit 作为 SFU。

#### 硬性要求 B：形象画面不能因待机/说话切换产生跳帧

这里分成两个完全独立的系统：

```text
A. 形象资产系统（后台）
B. 学生运行时系统（在线）
```

两者禁止强耦合。

##### A. 形象资产（管理端）

管理端人员可以：

- 上传 AI 形象视频 `avatar.mp4`；
- 触发预处理（转码 720P@25fps、抽帧、写 manifest）；
- 设置 `idle_frame / talk_start / talk_end`（可带默认推荐值）；
- 绑定默认音模 `voice_id`。

处理挂在学生端服务端内完成（上传后异步预处理）。

```text
管理端上传 avatar.mp4
        ↓
processing（转码 / 抽帧 / 写 Package）
        ↓
ready（可被新 Session 选用）
```

正在跑的 Session **不**因新上传而切换形象。

##### B. 学生运行时系统

学生进入会话时，只做：

```text
student session
      ↓
读取当前默认 avatar_version
      ↓
固定：
avatar_id
avatar_version_id
      ↓
加载已经处理好的 Avatar Package
      ↓
启动 Publisher
```

**Session 一旦启动，就固定使用这个 `avatar_version_id`。**

后台此时即使：

- 上传同一个形象的新视频；
- 修改 talking 区间；
- 重新转码；
- 改默认形象为 v2；

当前正在运行的学生 Session 仍然继续使用原来的 v1，不受任何影响。

例如：

```text
Avatar A

v1 = ready
       ↓
学生 01 正在使用 v1
学生 02 正在使用 v1

后台上传新视频
       ↓
v2 = processing
       ↓
v2 = ready
       ↓
v2 = ready

结果：

学生 01 → 继续 v1，直到 Session 结束
学生 02 → 继续 v1，直到 Session 结束
新进入学生 03 → 使用 v2
```

这就是生产环境必须采用的**版本锁定（version pinning）**。

##### 运行期无跳帧原则

运行中的 Publisher 只读取已经处理完成的 Avatar Package：

```text
Avatar Package
├── manifest.json
├── idle_frame
├── talking frame range / cache
└── metadata
```

运行时：

```text
IDLE
→ 输出 idle_frame

TTS START
→ Crossfade
→ talking frame loop

TTS END
→ Crossfade
→ idle_frame
```

WebRTC Session 内仍然保持：

```text
同一个 Video Track
同一个连续 FrameClock
同一个 Publisher 生命周期
```

这里“不切视频文件、不重建 Video Track”只描述**单个正在运行的 Session 内部**。

它绝不意味着：

> 后台不能上传新形象。

后台形象资产管理与在线 Session 完全是两条链路。

#### 硬性要求 C：本地 ASR 与本地 TTS 必须支持多路业务请求

ASR：

- 本地 FunASR；
- 非流式整段识别；
- 多学生同时松开录音时必须支持并发任务/排队调度；
- 不允许通过一个全局同步锁把所有学生长期串行阻塞。

TTS：

- 本地 CosyVoice3；
- 非流式整段合成（全文到齐后一次合成 PCM）；
- 必须存在 学生端 TTS Scheduler + 多 Worker 设计；
- 双 RTX 4090 48GB 都要可参与 TTS 工作；
- 多个学生可以同时处于 `speaking`；
- 每一路 TTS 必须拥有独立 `tts_request_id`、PCM Queue 和取消控制。

**具体双 4090 能稳定同时合成多少路，不在设计阶段拍脑袋写死，必须通过本文压测流程得到实际稳定并发值。**

#### 硬性要求 D：WebRTC 空闲必须自动释放

学生页面可以长时间打开，但 **WebRTC 媒体链路不能因为页面打开就永久占用**。

系统必须把：

```text
业务会话 Business Session
```

和：

```text
媒体会话 Media Session / WebRTC Session
```

拆开。

业务会话可以保留：

- `student_id`
- `conversation_id`
- `avatar_id`
- `avatar_version_id`
- 当前课程上下文
- 最近一次问答时间

但空闲一段时间后必须释放：

- LiveKit participant；
- Video Track；
- Audio Track；
- Publisher；
- PCM Queue；
- 视频 FrameClock；
- 当前媒体缓冲；
- 与本次媒体连接相关的内存资源。

学生再次发起问答时重新建立媒体会话。

### 1.2 首版业务约束

1. 每个学生一路 WebRTC。
2. 每个数字人只使用 **1 个 AI 生成视频文件**。
4. 学生采用“按住说话 / 点按录音”的一问一答模式。
5. 学生松开后，将完整录音上传后端。
6. ASR 使用本地非流式识别。
7. Dify 只作为已部署好的外部问答接口，本文不负责其部署。
8. TTS 使用本地非流式整段语音合成。
9. TTS 第一包可播放 PCM 就绪后进入 `speaking`。
10. TTS 完成、失败或被打断后回到 `idle`。
11. 视频状态切换不得导致 WebRTC Track 重建、PTS 回退、黑屏或花屏。

## 2. 首版整体技术选型

| 模块 | 默认实现 | 说明 |
|---|---|---|
| 浏览器采音 | MediaRecorder / Web Audio API | 长按或点按录音 |
| 录音上传 | HTTP POST multipart | 完整录音上传 |
| ASR | FunASR `paraformer-zh` | 本地、非流式整段识别 |
| VAD | `fsmn-vad` | ASR 预处理，可选但建议启用 |
| 标点 | `ct-punc` | 最终文本标点恢复 |
| 问答 | Dify API | 已部署外部服务，仅调用 |
| Dify 输出 | Streaming | 尽早驱动 TTS |
| TTS | `Fun-CosyVoice3-0.5B-2512` | 本地、非流式整段合成 |
| GPU | **2 × RTX 4090 48GB** | 双卡主要服务 TTS，ASR 与 GPU0 共享或后续转 CPU |
| 学生端 Avatar 素材 | **单个 `avatar.mp4`** | AI 生成；固定机位人物自然讲话 |
| 学生端 Avatar 运行参数 | `idle_frame / talk_start / talk_end` | 上传后确定，不依赖 AI 精确生成帧号 |
| 视频控制 | `学生端 AvatarFrameController` | 按状态取帧 |
| 视频时间轴 | 独立连续 `FrameClock` | 25 FPS，PTS 永不因素材循环而重置 |
| WebRTC | LiveKit | SFU，多路 Session |
| 学生端 Publisher | 每学生一个逻辑实例 | 一个长期 Video Track + 一个长期 Audio Track |
| 内部 TTS 调度 | 学生端 TTS Scheduler + GPU Workers | 多路并发、负载分配、取消 |
| 内部 ASR 调度 | ASR Queue + Worker | 突发多任务 |
| 服务编排 | Python / FastAPI 推荐 | 可替换为现有后端技术栈 |
| 队列 | asyncio Queue；规模扩大后 Redis | 任务隔离与削峰 |

**视频方案只有这一套，不再保留双视频、多视频或多模式分支。**

## 3. 核心业务流程

### 3.1 一轮完整问答

```text
学生浏览器
   │
   │ ① 按住/点按开始录音
   ▼
本地录音
   │
   │ ② 松开 / 点击结束
   ▼
上传完整音频
   │
   │ POST /api/v1/sessions/{session_id}/questions
   ▼
业务 API
   │
   │ ③ 音频规范化
   ▼
学生端 ASR 服务
Paraformer-zh
   │
   │ ④ 最终识别文本
   ▼
业务 API
   │
   │ ⑤ 请求 Dify
   ▼
Dify Streaming
   │
   │ ⑥ 文本增量
   ▼
TTS Text Chunker
   │
   │ ⑦ 按标点/长度聚合
   ▼
学生端 TTS Scheduler
   │
   ├────────► GPU 0 / CosyVoice Worker
   └────────► GPU 1 / CosyVoice Worker
                   │
                   │ ⑧ PCM chunks
                   ▼
               学生端 Publisher
                   │
          首个可播放音频包
                   │
        idle ──────┴──────► speaking
                   │
                   ▼
      学生端 AvatarFrameController + TTS
                   │
       idle：重复 idle_frame
       speaking：循环 talk_start → talk_end
       切换：程序生成短 Crossfade
                   │
              TTS 完成
                   ▼
          平滑回到 idle 状态
```

### 3.2 关键设计

ASR 与 TTS 的实时性要求不同。

**ASR 不需要流式。**

学生只有在松开录音按钮后才发起识别，因此 ASR 收到的是一个已经结束的完整音频文件。后端只需要尽快返回一次最终文本。

**TTS 不要流式：等 Dify 全文到齐后整段合成。**

业务约定：

```text
Dify 全文
      ↓
POST /internal/tts/synthesize（整段）
      ↓
完整 PCM
      ↓
学生端 Publisher 按帧推送 / 浏览器收听
```

首句开口延迟换吞吐：多 Worker 并行服务多路整段合成，避免流式长占 GPU。

## 4. 服务划分

建议拆成 5 个逻辑服务。

```text
┌─────────────────────────────────────────────┐
│                 学生端 Web                     │
└───────────────┬─────────────────────────────┘
                │
                ▼
┌─────────────────────────────────────────────┐
│              学生端服务端                   │
│ session / avatar / question / interrupt     │
└──────┬─────────────┬───────────────┬────────┘
       │             │               │
       ▼             ▼               ▼
┌────────────┐  ┌────────────┐  ┌──────────────┐
│ 学生端 ASR 服务│  │ Dify Adapter│  │学生端 TTS Scheduler │
└────────────┘  └────────────┘  └───────┬──────┘
                                        │
                            ┌───────────┴───────────┐
                            ▼                       ▼
                     学生端 TTS Worker 0             学生端 TTS Worker 1
                        GPU 0                     GPU 1
                            └───────────┬───────────┘
                                        ▼
                                 学生端 Publisher Pool
                                        │
                                        ▼
                                    LiveKit
```

### 4.1 学生端服务端

职责：

- 学生端 Avatar CRUD。
- 创建/销毁学生 Session。
- 接收学生录音。
- 创建 `question_id`。
- 调用 ASR。
- 调用 Dify。
- 将 Dify 文本流送入 TTS Chunker。
- 调用 学生端 TTS Scheduler。
- 管理问答取消。
- 管理 session 状态。
- 向 学生端 Publisher 发送 `start_speaking` / `stop_speaking`。
- 暴露监控指标。

学生端服务端 **不直接加载语音模型**。

### 4.2 学生端 ASR 服务

职责：

- 加载 Paraformer。
- 可选加载 FSMN-VAD。
- 加载 CT-Punc。
- 接收完整音频。
- 音频预处理。
- 完成离线识别。
- 返回最终文本。
- 暴露耗时和队列指标。

### 4.3 Dify Adapter

对接**外部已部署的 Dify**（本仓库不部署 Dify / 大模型）。

配置：

```text
DIFY_BASE_URL=http://117.50.223.142:7000
DIFY_API_KEY=<应用 API Key>
```

智能体名称以 Dify `GET /v1/info` 的 `name` 为准。当前应用：

```text
name = 聊天机器人
mode = advanced-chat
接口文档：http://117.50.223.142:7000/app/37af7546-8513-4953-ab8f-2ec3ced2cf5a/develop
```

职责：

```text
业务请求
  ↓
POST /v1/chat-messages（streaming）
  ↓
文本事件 → TTS
```

支持按 `task_id` 取消（`POST /v1/chat-messages/{task_id}/stop`）。  
更换智能体：在 Dify 新建/切换应用后，把新 API Key 写入 `.env` 并重启业务 API；名称自动从 `/v1/info` 刷新。

### 4.4 学生端 TTS Scheduler

职责：

- 接收新的 TTS Job。
- 为 Job 分配 Worker。
- 维护 Worker 当前负载。
- 做每学生顺序控制。
- 支持取消。
- 输出完整 PCM（非流式整段）；
- 记录合成耗时与取消。

### 4.5 学生端 Publisher

每个活跃学生对应一个逻辑 学生端 Publisher。

学生端 Publisher 必须是**长期存在的连续媒体生产器**，而不是 MP4 播放器。

职责：

- Session 创建时创建一次 LiveKit Video Track；
- Session 创建时创建一次 LiveKit Audio Track；
- 生命周期内不因 `idle/speaking` 重建 Track；
- 调用 `学生端 AvatarFrameController` 每 40ms 获取一帧；
- 使用独立 `FrameClock` 生成连续输出 PTS；
- `idle` 状态重复输出 `idle_frame`；
- `speaking` 状态循环输出 `[talk_start, talk_end]`；
- 状态切换时由程序生成 3～5 帧 Crossfade；
- 将 CosyVoice PCM 持续写入本 Session 的音频队列；
- TTS 完成或打断时清空当前 PCM Queue；
- 所有帧和音频块都绑定当前 `session_id / question_id / generation`；
- 旧 generation 的迟到帧或 PCM 一律丢弃。

学生端 Publisher 不做：

- 运行时 seek MP4；
- 直接切两个 H.264 码流；
- 切换时重启编码器；
- 切换时重新 publish Video Track；
- 复用其他学生的 PCM Queue。


### 4.6 管理端：形象上传 / 预处理

挂在学生端服务端，职责仅：

- 上传原始 `avatar.mp4`；
- 异步预处理：探测、转码 720P@25fps、抽帧、写 `idle.png` + `manifest.json`；
- 列表 / 设为默认形象；
- 可选覆盖 `idle_frame / talk_start / talk_end` 后重写 manifest。

状态只需：`processing` → `ready`（或 `failed`）。

预处理不得修改正在运行的 Publisher / Session。

### 4.7 管理端：音模

- 上传参考音频（wav）+ 提示文本 → 注册 `voice_id`；
- 列表 / 设为默认音模；
- TTS Worker 加载或热注册该音模后，问答链路按 `voice_id` 合成。

## 5. ASR 开发方案

> 学生端 ASR 只负责：**完整录音 → 最终文字**。  
> 不做热词、不做持续监听、不做流式识别、不做情感识别、不做说话人分离。


### 5.1 默认模型

默认：

```text
paraformer-zh
```

辅助模型：

```text
fsmn-vad
ct-punc
```

用途：

```text
完整学生录音
    ↓
FSMN-VAD
    ↓
Paraformer
    ↓
CT-Punc
    ↓
最终文本
```

首版不使用：

```text
paraformer-zh-streaming
```

原因不是模型不好，而是业务只需完整录音后的最终文字。

### 5.2 推荐输入音频规范

浏览器可以录制 WebM/Opus，但 学生端 ASR 服务 内部统一转换。

内部统一格式：

```text
sample rate: 16000 Hz
channels:    1
sample:      signed int16
format:      WAV / PCM
```

后端收到：

```text
audio/webm
audio/wav
audio/ogg
```

均先经过 ffmpeg 规范化。

示例：

```bash
ffmpeg -i input.webm \
  -ac 1 \
  -ar 16000 \
  -c:a pcm_s16le \
  output.wav
```

### 5.3 音频长度限制

首版建议：

```text
最短有效录音：300 ms
正常建议上限：60 s
硬上限：120 s
```

超过硬上限直接拒绝或提示学生重新提问。

避免因为误操作上传几分钟甚至更长录音，占用 ASR 队列。

### 5.4 ASR 服务接口

```http
POST /internal/asr/transcribe
Content-Type: multipart/form-data
```

参数：

```text
audio           required    音频文件
session_id      required
question_id     required
language        optional    默认 zh
```

响应：

```json
{
  "code": 0,
  "request_id": "asr_xxx",
  "session_id": "sess_xxx",
  "question_id": "q_xxx",
  "text": "为什么天空是蓝色的？",
  "duration_ms": 4380,
  "processing_ms": 126
}
```


### 5.5 ASR 并发模型

不需要为 30 个在线学生长期保持 30 个 ASR 模型 session。

实际模型：

```text
30 students online
        ↓
只有松开录音时创建 ASR job
        ↓
ASR Queue
        ↓
1~N inference workers
```

极端情况：

```text
30 人同时松开录音
        ↓
30 ASR jobs
        ↓
短队列 + batch / 快速串行消费
```

目标不是“30 个 ASR 常驻连接”，而是“30 个短音频任务在可接受时间内消化”。

### 5.6 ASR 超时建议

```text
排队超时：       3 s
单任务识别超时： 5 s
整体接口超时：   8 s
```

如果常见 3～10 秒学生提问在上述超时内无法稳定返回，需要扩 Worker 或优化 Runtime。

## 6. TTS 开发方案

### 6.1 默认模型

默认：

```text
Fun-CosyVoice3-0.5B-2512
```

要求：

- 本地部署；
- 支持中文；
- 支持数字人固定音色；
- 业务侧使用 HTTP 整段合成，不依赖 text-in / audio-out streaming；
- 支持取消；
- 支持多 Worker。

### 6.2 为什么 TTS 必须独立服务化

TTS 与 ASR 不同：

ASR：

```text
一个完整音频
→ 一次计算
→ 一个文本
```

TTS：

```text
一段完整回答文本
→ 一次整段合成
→ 一段完整 PCM
→ Publisher 播放
```

一路 speaking 会占用一个 TTS Worker 直至该段合成结束，因此双 GPU 多 Worker 优先服务 TTS。

### 6.3 TTS 内部接口（非流式主路径）

```http
POST /internal/tts/synthesize
Content-Type: application/json
```

```json
{
  "text": "天空之所以呈现蓝色，主要与太阳光在大气中的散射有关。",
  "voice_id": "avatar_voice_001",
  "session_id": "sess_xxx",
  "question_id": "q_xxx"
}
```

返回 PCM（base64）+ `sample_rate`。业务 API 收到完整 PCM 后再推 LiveKit。

取消：业务侧丢弃该 `question_id` 的 generation，并尽量中断正在进行的 HTTP 合成任务。

> WS `/internal/tts/stream` 仅遗留，首版业务链路不使用。

### 6.4 文本与合成时机

业务侧 **等 Dify 全文到齐** 后再调用 TTS，不做按句切块流式喂入。

可选：极长回答再按段落拆成多次 HTTP 合成；首版默认一次全文。

### 6.5 画面状态切换

```text
TTS HTTP 返回完整 PCM
→ 学生端 AvatarFrameController: IDLE → TRANSITION → TALKING
→ Publisher 按帧推送 PCM
```

禁止在 TTS 尚未返回前进入 talking。不切 MP4、不 seek、不重建 Video Track。

### 6.6 TTS 结束

```text
PCM 已全部推入 Publisher 且播放缓冲耗尽
→ speaking → idle
```

打断时：丢弃当前 generation，清空 PCM queue，回 idle。

## 7. 双 RTX 4090 48GB 资源设计

### 7.1 推荐方式

两张 GPU 都作为主要 TTS 资源。

```text
GPU 0
├── CosyVoice Worker 0
└── ASR Worker（共享 / 按需）

GPU 1
└── CosyVoice Worker 1
```

原因：

- Paraformer 约 220M，属于短时任务；
- ASR 非流式，没有长连接；
- TTS Job 会持续产生音频；
- TTS 的实时率和并发更容易成为系统瓶颈。

### 7.2 首版进程建议

先不要一开始开大量进程。

建议：

```text
GPU 0:
  cosyvoice-worker-0
  asr-worker-0

GPU 1:
  cosyvoice-worker-1
```

压测以后根据实际 GPU Util / VRAM / RTF 再决定：

```text
每卡 1 学生端 TTS Worker
或
每卡 2 学生端 TTS Worker
```

不要仅根据“显存还有很多”判断可以继续加实例。

真正限制往往是：

```text
GPU compute
实时率 RTF
调度
KV/cache
音频生成速度
请求长度
```

### 7.3 TTS 调度

学生端 TTS Scheduler 维护：

```json
{
  "worker_0": {
    "gpu": 0,
    "active_jobs": 2,
    "queued_jobs": 0
  },
  "worker_1": {
    "gpu": 1,
    "active_jobs": 1,
    "queued_jobs": 0
  }
}
```

首版可采用：

```text
least_active_jobs
```

即哪个 Worker 当前活跃任务少就分给哪个。

后续可以升级为：

```text
weighted least load
```

加入：

- 当前音频生成 RTF；
- 当前 GPU Util；
- GPU Memory；
- 当前待生成文本长度；
- Job 已运行时长。

## 9. 打断机制

首版虽然不是持续聆听，但仍然需要打断。

触发方式：

1. 学生点击“停止回答”；
2. 数字人讲话时学生再次按下录音按钮；
3. 前端主动发 interrupt。

接口：

```http
POST /api/v1/sessions/{session_id}/interrupt
```

处理顺序：

```text
interrupt
   ↓
标记 current question cancelled
   ↓
取消 Dify stream（如果仍在输出）
   ↓
取消 CosyVoice job
   ↓
清空 学生端 Publisher PCM queue
   ↓
停止当前 TTS PCM 输出
   ↓
学生端 AvatarFrameController:
当前 talking frame → Crossfade → idle_frame
   ↓
state = idle
```

必须确保旧请求后续迟到的 PCM 不会再次播放。

因此每个音频块都必须绑定：

```text
session_id
question_id
tts_request_id
generation
```

学生端 Publisher 只接受当前 generation。

## 12. 单视频 学生端 Avatar 与 WebRTC 无跳帧实现

### 12.1 唯一视频方案

每个学生端 Avatar 只有：

```text
avatar.mp4
```

AI 视频只负责提供：

- 一个固定机位的人物；
- 第一帧附近存在稳定的闭嘴/待机姿态；
- 后续存在一段自然连续的讲话动作；
- 人物、背景、光线、构图尽量稳定。

**系统不要求 AI 精确生成 `idle / transition / talk / transition` 四个固定时间段。**

AI 是素材生成器，不是运行时状态机。

上传后系统把成品视频变成确定性的运行参数：

```text
idle_frame
talk_start
talk_end
```

运行时只认这三个值。

---

### 12.2 AI 生成视频的硬性素材条件

形象原始视频要求：

#### 必须满足

1. **固定摄像机**
   - 不推镜；
   - 不拉镜；
   - 不摇镜；
   - 不变焦；
   - 不切镜头。

2. **人物位置稳定**
   - 人脸中心不要明显漂移；
   - 肩膀和身体中心不要突然移动；
   - 人物尺寸不能变化。

3. **背景稳定**
   - 背景内容不变；
   - 不出现新物体；
   - 不发生明显景深或透视变化。

4. **光照稳定**
   - 不闪烁；
   - 不突然变亮或变暗；
   - 肤色保持稳定。

5. **视频开始时提供标准待机姿态**
   - 正面看镜头；
   - 嘴巴自然闭合；
   - 表情自然；
   - 头部和肩膀稳定。

6. **后续提供自然讲话动作**
   - 嘴部自然开合；
   - 可轻微眨眼；
   - 可非常轻微点头；
   - 避免大幅手势；
   - 避免身体明显左右移动。

7. **说话动作中存在一段相对稳定、可循环的区间**
   - 不要求 AI 自己做完美 Loop；
   - 系统上传后从成品中选择最合适的 `talk_start / talk_end`；
   - 循环点仍由程序 Crossfade 处理。

#### 建议输出规格

```text
时长：不强制；开头应为闭嘴待机，随后进入说话嘴型
分辨率：1280×720 或更高
帧率：25fps（上传后统一为 25fps）
人物：半身或胸像
镜头：正面固定
背景：固定
```

---


### 12.3 为什么不能相信 AI 精确帧号

禁止设计成：

```text
要求 AI：
0～49 帧一定待机
50～57 帧一定过渡
58～132 帧一定讲话
133～140 帧一定结束
```

生成式视频无法作为这种帧级确定性来源。

正确设计：

```text
AI 生成 avatar.mp4
        ↓
系统分析 / 人工预览
        ↓
idle_frame = 实际选中的一张稳定待机帧
talk_start = 实际选中的讲话循环起点
talk_end   = 实际选中的讲话循环终点
        ↓
保存为 学生端 Avatar Manifest
```

一旦 Manifest 保存，**运行时完全确定**，不再依赖 AI。

---

### 12.4 上传预处理

上传 学生端 Avatar 后只处理一次。

流程：

```text
avatar.mp4
   ↓
ffprobe / 解码检查
   ↓
规范化 720P@25fps
   ↓
生成帧索引
   ↓
生成预览缩略帧
   ↓
自动推荐：
idle_frame
talk_start
talk_end
   ↓
管理员预览确认
   ↓
建立 学生端 Avatar Frame Cache
```

推荐首版不要做复杂 AI 自动分析。

最稳的管理端交互：

```text
[视频预览]

Idle Frame :  [滑块]
Talk Start :  [滑块]
Talk End   :  [滑块]

[预览待机]
[预览 Talking 循环]
[保存]
```

人工只需要设置一次。

---

### 12.5 学生端 Avatar Manifest

```json
{
  "avatar_id": "avatar_001",
  "source": "avatar.mp4",
  "fps": 25,
  "width": 1280,
  "height": 720,
  "idle_frame": 3,
  "talk_start": 21,
  "talk_end": 121,
  "transition_frames": 4
}
```

其中：

- `idle_frame`：待机时重复输出；
- `talk_start`：说话循环第一帧；
- `talk_end`：说话循环最后一帧；
- `transition_frames`：待机/说话切换时程序生成的 Crossfade 帧数。

---

### 12.6 Session 启动时的加载

Session 启动时：

```text
读取 学生端 Avatar Manifest
        ↓
加载/预解码该 学生端 Avatar 所需帧
        ↓
学生端 AvatarFrameController Ready
        ↓
创建 LiveKit VideoSource
        ↓
创建 LocalVideoTrack
        ↓
publish 一次
```

之后直到 Session 关闭：

```text
Video Track 永远不重建
```

#### 缓存建议

素材较短（数秒级）时，首版优先采用：

```text
预解码帧缓存
```

这样状态切换时：

- 不读磁盘；
- 不 seek；
- 不等待关键帧；
- 不临时启动 Decoder。

如果全量 raw frame 内存过大，再优化为：

```text
idle_frame 常驻
+
talk 区间预解码 ring buffer
```

首版先以稳定性优先。

---

### 12.7 WebRTC 连续 FrameClock

25 FPS：

```text
1 frame = 40ms
```

学生端 Publisher 自己维护：

```text
output_frame_index = 0,1,2,3...
```

输出时间戳：

```text
0ms
40ms
80ms
120ms
...
```

素材帧序号可以循环：

```text
talk 21 → 22 → ... → 121 → 21 → 22 ...
```

但 WebRTC PTS 绝对不能循环：

```text
输出 PTS：
83040ms
83080ms
83120ms
83160ms
...
```

因此：

> **素材时间轴与 WebRTC 输出时间轴完全分离。**

这是“不跳帧”的核心工程原则。

---

### 12.8 IDLE 状态

数字人不说话时：

```text
state = IDLE
```

程序每 40ms：

```text
取 idle_frame
↓
复制/引用成当前输出帧
↓
赋新的连续 PTS
↓
VideoSource.capture_frame()
```

外部看到：

```text
同一张待机画面
+
持续正常 25fps WebRTC Track
```

不是暂停视频轨。

这样：

- WebRTC Track 一直活着；
- 浏览器不用等重新出关键帧；
- 不存在切文件；
- 不存在重新协商。

---

### 12.9 TTS 开始：IDLE → TALK

触发条件：

```text
CosyVoice 第一包可播放 PCM 已 Ready
```

流程：

```text
当前 idle_frame
    ↓
生成 transition_frames 个 Crossfade
    ↓
进入 talk_start
    ↓
talk_start → ... → talk_end 循环
```

例如 4 帧 Crossfade：

```text
F0 = 75% idle + 25% talk_start
F1 = 50% idle + 50% talk_start
F2 = 25% idle + 75% talk_start
F3 = 100% talk_start
```

Crossfade 是程序生成，不依赖 AI 视频里存在过渡片段。

同时对 TTS PCM 做很小预缓冲：

```text
约 80～150ms
```

目标：

```text
视觉开始动嘴
≈
声音真正开始播放
```

---

### 12.10 TALK 状态

```text
state = SPEAKING
```

FrameController：

```text
talk_start
talk_start + 1
...
talk_end
```

如果 TTS 还没结束：

```text
talk_end
↓
Crossfade 到 talk_start
↓
重新循环
```

因此无论回答：

```text
2 秒
10 秒
30 秒
```

都只需要这一段讲话素材。

---

### 12.11 Talking 循环点防跳帧

AI 生成的视频首尾不会百分百一致。

因此禁止：

```text
talk_end → talk_start
```

硬切。

必须使用：

```text
3～5 帧短 Crossfade
```

推荐：

```text
transition_frames = 4
```

25 FPS 时约：

```text
160ms
```

如果选取的 talk 循环点本身已经非常接近，可以降低到 2～3 帧。

---

### 12.12 TTS 结束：TALK → IDLE

TTS 播放真正结束时：

```text
当前 talking frame
      ↓
3～5 帧 Crossfade
      ↓
idle_frame
      ↓
持续重复 idle_frame
```

不要求 talking 视频必须回到闭嘴状态。

因此：

> **TTS 在任何 talking frame 结束都可以安全退出。**

---

### 12.13 打断

用户打断：

```text
interrupt
   ↓
generation + 1
   ↓
cancel Dify
   ↓
cancel TTS
   ↓
清空该 Session PCM Queue
   ↓
丢弃旧 generation 的音频
   ↓
当前 talking frame Crossfade → idle_frame
   ↓
state = IDLE
```

整个过程中：

```text
Video Track 不重建
Audio Track 不重建
WebRTC 不重新协商
```

### 12.14 学生端 AvatarFrameController 状态机

只有三个内部状态：

```text
IDLE
TRANSITION
TALKING
```

逻辑：

```text
                 ┌─────────────┐
                 │             │
                 ▼             │
              IDLE             │
                 │             │
          TTS audio ready      │
                 ▼             │
            TRANSITION         │
                 ▼             │
             TALKING ─────┐    │
                 ▲        │    │
                 └────────┘    │
                 │             │
          TTS end/interrupt    │
                 ▼             │
            TRANSITION         │
                 └─────────────┘
```

没有第四个视频，没有第二个 MP4，没有 seek。

---

### 12.15 核心伪代码

```python
FRAME_INTERVAL = 1 / 25

while session.active:
    if state == IDLE:
        source_frame = avatar.idle_frame

    elif state == TALKING:
        source_frame = avatar.frames[talk_index]
        talk_index += 1

        if talk_index > avatar.talk_end:
            begin_talk_loop_crossfade()
            talk_index = avatar.talk_start

    elif state == TRANSITION:
        source_frame = transition.next_frame()

    output_frame = attach_continuous_pts(
        source_frame,
        frame_clock.next()
    )

    await video_source.capture_frame(output_frame)
    await sleep_until_next_40ms()
```

实际实现时不要用普通 `sleep(0.04)` 累积漂移，应使用基于 monotonic clock 的 deadline 调度。

---

### 12.16 无跳帧验收标准

必须同时满足：

```text
video_track_recreate_count = 0
video_pts_discontinuity_count = 0
```

并且：

- IDLE → TALKING 无黑屏；
- TALKING → IDLE 无黑屏；
- talking 循环无明显人物瞬移；
- interrupt 后无黑屏；
- 不出现旧 talking 帧重新恢复；
- WebRTC 不重新协商；
- 视频 FPS 在切换前后连续；
- 不因素材 loop 重置 PTS。

这部分属于**硬验收项**，不是主观优化项。

## 13. Dify 接口边界

Dify 为外部服务。Dify Adapter 提供：

```python
async def stream_answer(
    session_id: str,
    question_id: str,
    text: str,
    context: dict
) -> AsyncIterator[str]:
    ...
```

输出只需要是：

```text
文本增量
```

例如：

```text
天空之所以
呈现蓝色，
主要是因为
...
```

学生端服务端 负责将其送进 TTS Text Chunker。

需要支持：

```python
cancel(question_id)
```

这样 interrupt 时可以停止无意义的后续生成。

## 13.5 WebRTC 媒体会话生命周期与空闲回收

### 13.5.1 为什么必须回收

如果 30+ 学生只是把页面挂着，数字人没有进行任何问答，但后台仍然保持：

```text
30+ Publisher
30+ Video Track
30+ Audio Track
30+ WebRTC 连接
```

会持续占用：

- SFU 连接资源；
- 服务端内存；
- Publisher 调度资源；
- 视频编码/发送资源；
- 上行带宽；
- 浏览器下行带宽。

因此学生“在线”不能等价于“媒体连接永久在线”。

---

### 13.5.2 唯一运行策略

采用：

```text
Business Session 长生命周期
+
Media Session 按需建立、空闲自动释放
```

#### 页面初次打开

只建立轻量业务会话：

```text
Business Session
```

浏览器通过普通 HTTP/CDN 加载该 Avatar 的：

```text
idle_frame
```

页面直接显示待机画面。

**此时不建立 WebRTC。**

---

### 13.5.3 学生开始录音时预热 WebRTC

学生按下“按住说话”按钮时同时做两件事：

```text
A. 浏览器开始本地录音
B. 后台 ensure_media_session()
```

流程：

```text
pointer/touch down
      │
      ├── 开始 MediaRecorder
      │
      └── POST /sessions/{id}/media/ensure
                    ↓
             创建 LiveKit participant
                    ↓
             启动学生端 Publisher
                    ↓
             加载已锁定 avatar_version
                    ↓
             publish Video/Audio Track
                    ↓
                media_ready
```

这样 WebRTC 建链时间被隐藏在：

```text
学生说话时间
+
ASR 时间
+
Dify 首 token 时间
```

之中。

通常在 TTS 第一包音频到达之前，媒体链路已经建立完成。

---

### 13.5.4 学生松开录音后

```text
录音结束
   ↓
上传完整音频
   ↓
本地 ASR
   ↓
Dify（凑齐全文）
   ↓
CosyVoice 整段合成
   ↓
完整 PCM → Publisher 播放
```

在进入 TTS 播放前必须检查：

```text
media_session.state == ready
```

如果媒体还没 Ready：

```text
允许极短等待
```

但不能在媒体未就绪时丢弃已合成的 PCM。

---

### 13.5.5 回答结束后的 Warm Idle

每次 TTS 完成后，不立即断开 WebRTC。

进入：

```text
MEDIA_WARM_IDLE
```

保留一小段时间，方便学生连续追问。

建议默认：

```text
MEDIA_IDLE_TIMEOUT = 90 秒
```

这是配置项，不写死在代码。

在这 90 秒内，如果学生再次开始录音：

```text
直接复用当前 Media Session
```

无需重新建链。

---

### 13.5.6 90 秒无交互后自动释放

如果满足：

```text
now - last_user_or_tts_activity >= MEDIA_IDLE_TIMEOUT
```

则：

```text
MEDIA_WARM_IDLE
      ↓
停止 Publisher
      ↓
unpublish Audio Track
      ↓
unpublish Video Track
      ↓
leave LiveKit
      ↓
释放 PCM Queue
      ↓
释放 FrameClock / media buffers
      ↓
media_session = CLOSED
```

但保留：

```text
Business Session
conversation_id
avatar_version_id
课程上下文
```

因此下次学生再次提问时仍然是同一个逻辑对话。

---

### 13.5.7 WebRTC 断开后页面显示什么

浏览器不能黑屏。

当 Media Session 被释放时：

```text
WebRTC video hidden
        ↓
显示通过 HTTP/CDN 已加载的 idle_frame
```

因此学生看到的仍然是数字人待机画面。

只有进入媒体会话后：

```text
idle_frame UI
    ↓
WebRTC Video Track Ready
    ↓
无感切到 WebRTC video
```

回答结束并超时释放时：

```text
WebRTC idle frame
    ↓
切回同一 Avatar 的 HTTP idle_frame
    ↓
关闭 WebRTC
```

因为两边使用的是**同一个 Avatar Package 的 idle_frame**，视觉切换应保持一致。

---

### 13.5.8 业务会话与媒体会话状态

业务会话：

```text
ACTIVE
CLOSED
```

媒体会话：

```text
CLOSED
CONNECTING
READY
SPEAKING
WARM_IDLE
RELEASING
```

关系：

```text
Business ACTIVE
    │
    ├── Media CLOSED
    │
    ├── Media CONNECTING
    │
    ├── Media READY
    │
    ├── Media SPEAKING
    │
    └── Media WARM_IDLE
```

业务会话存在，不代表 WebRTC 必须存在。

---

### 13.5.9 活动时间刷新条件

以下事件刷新：

```text
last_media_activity_at
```

- 学生开始录音；
- 学生提交录音；
- ASR 开始/完成；
- Dify 正在为该问题生成；
- TTS 开始；
- TTS 播放中；
- TTS 完成；
- interrupt。

只要当前存在未完成问题，禁止 Idle Reaper 错误释放媒体会话。

---

### 13.5.10 Idle Reaper

学生端服务端运行独立轻量任务：

```text
MediaSessionReaper
```

周期扫描：

```text
media_session.state == WARM_IDLE
```

并检查：

```text
idle_duration >= MEDIA_IDLE_TIMEOUT
```

满足条件才释放。

Reaper 不负责：

- 删除 Business Session；
- 删除 Dify conversation；
- 修改 avatar_version；
- 删除学生数据。

---

### 13.5.11 重新连接

Media Session 已关闭后，学生再次按下录音：

```text
Business Session 仍存在
        ↓
读取 session.avatar_version_id
        ↓
重新加载同一个 Avatar Package
        ↓
创建新的 Media Session
        ↓
重新 publish WebRTC Tracks
```

如果管理端已将默认形象改为 v2：

```text
当前 Business Session 仍使用原先锁定的 v1
```

除非业务会话本身结束后重新创建。

---

### 13.5.12 关键配置

```text
MEDIA_IDLE_TIMEOUT = 90s
MEDIA_CONNECT_TIMEOUT = 5s
MEDIA_RELEASE_GRACE = 1s
```

首版建议把 `MEDIA_IDLE_TIMEOUT` 做成后台配置。

后续根据真实课堂行为调整到：

```text
60～180 秒
```

但系统架构不改变。

---

### 13.5.13 验收要求

必须验证：

1. 页面打开 10 分钟但无操作：
   - 不存在持续 WebRTC Publisher；
   - 不持续发送视频带宽。

2. 学生开始录音：
   - 自动创建 Media Session；
   - 不要求刷新页面。

3. 连续追问：
   - 在 Warm Idle 期间复用现有 WebRTC。

4. 超过 Idle Timeout：
   - Publisher 自动释放；
   - LiveKit participant 退出；
   - 页面仍显示 Avatar idle_frame。

5. 再次提问：
   - 自动重新建立 WebRTC；
   - Dify conversation 上下文仍然存在；
   - avatar_version_id 不变化。

6. 30+ 学生页面全部打开但都不说话：
   - WebRTC 媒体资源接近 0 路活跃；
   - 只保留轻量 Business Session。

## 14. 多路并发设计

### 14.1 并发对象必须区分

系统有三种完全不同的“多路”：

```text
A. WebRTC 多路在线
B. ASR 多任务并发
C. TTS 多路实时合成
```

不能用一个“30 并发”数字混为一谈。

---

### 14.2 WebRTC 多路

目标：

```text
单班 30+ 学生
=
30+ 独立 Session
=
30+ 独立 学生端 Publisher
```

每个 Session 至少包含：

```text
1 Video Track
1 Audio Track
1 学生端 AvatarFrameController
1 FrameClock
1 PCM Queue
1 generation
```

必须按 Session 隔离。

WebRTC 多路与 GPU TTS 并发不是同一个概念：

30 个学生在线时，大量 Session 可能处于：

```text
IDLE
```

此时仍然保持 WebRTC 视频轨，但不占用 学生端 TTS Worker。

---

### 14.3 ASR 多路

ASR 是：

```text
录音完成后
→ 一次短任务
→ 返回最终文本
```

每次提问一次完整识别，不长期占用 ASR session。

结构：

```text
多个学生同时上传
        ↓
     ASR Queue
        ↓
  ASR Worker Pool
        ↓
    Paraformer
```

极端压测：

```text
30 个学生近似同时松开录音
```

必须做到：

- 请求不会互相覆盖；
- 每个任务独立 request_id；
- 队列不会阻塞 学生端服务端 event loop；
- ASR 失败只影响当前问题；
- 可配置最大队列长度；
- 有排队超时；
- 有任务取消/Session 已关闭检查。

ASR 可以允许短排队，因为它不是实时音频播放任务。

---

### 14.4 TTS 多路

TTS 是最重要的 GPU 并发资源。

结构：

```text
Dify streams
    │
    ▼
TTS Text Chunker
    │
    ▼
学生端 TTS Scheduler
    │
    ├── GPU0 Worker(s)
    └── GPU1 Worker(s)
```

每个 TTS Job 独立维护：

```text
session_id
question_id
tts_request_id
generation
voice_id
text_queue
pcm_queue
cancel_event
started_at
```

硬性要求：

- 多个学生可以同时处于 `speaking`；
- 禁止全局只有一个 TTS Job；
- 一个 Job cancel 不影响其他 Job；
- GPU0/GPU1 都可接收任务；
- Scheduler 根据 Worker 当前负载分配；
- 每个 Session 的文本与 PCM 顺序必须保持；
- 不同 Session 之间允许并行。

---

### 14.5 双 4090 资源分配

机器：

```text
GPU0 = RTX 4090 48GB
GPU1 = RTX 4090 48GB
```

默认：

```text
GPU0
├── CosyVoice 学生端 TTS Worker
└── Paraformer ASR Worker

GPU1
└── CosyVoice 学生端 TTS Worker
```

如果压测发现：

```text
ASR burst
→ GPU0 TTS 整段合成耗时 抖动
```

则第二阶段把 ASR 调整为：

```text
CPU / ONNX Runtime
```

让：

```text
GPU0 → TTS
GPU1 → TTS
```

两张卡都专门服务实时合成。

---

### 14.6 不提前承诺一个虚假的“TTS 30 路同时说话”

项目要求：

```text
30+ WebRTC 在线
```

并不自动等于：

```text
30 路 CosyVoice 必须同时实时合成
```

双 4090 的**稳定实时 TTS speaking 并发**必须通过目标模型、目标音色、目标文本长度、目标采样率的真实压测获得。

最终部署参数记为：

```text
MAX_TTS_ACTIVE_JOBS = benchmark_result
```

只有满足：

```text
RTF < 1
整段合成耗时达标
无持续爆显存
无明显断音
```

的并发档位才能作为生产上限。

---

### 14.7 TTS 队列策略

TTS 与 ASR 不同，不能允许长时间排队。

建议配置：

```text
tts_queue_warn_ms
tts_queue_fail_ms
max_tts_active_jobs
```

超过最大实时 speaking 数时：

```text
短时间排队
```

如果达到 fail threshold：

- 返回“当前使用人数较多，请稍后再试”；
- 或业务层限制同班同时问答；
- 后续增加 GPU 节点横向扩容。

**不能为了“看起来支持 30 路”让所有 TTS 都降到 RTF > 1。**

---

### 14.8 多路隔离原则

所有异步数据必须带：

```text
session_id
question_id
generation
```

TTS 再额外带：

```text
tts_request_id
```

ASR 再额外带：

```text
asr_request_id
```

任何 Worker 返回结果前必须检查当前 generation。

这样可以避免：

```text
学生 A 的旧回答
→ 在学生 A 新一轮问题中突然播放
```

更不能出现跨学生串音。

## 23. 最终默认架构

系统明确拆成两个平面。

### 23.1 管理端平面（非实时）

```text
管理端页 /admin
   ├─ 上传 avatar.mp4 → 预处理 → Avatar Package (ready)
   └─ 上传音模 wav → 注册 voice_id → TTS 可用
```

与学生实时 WebRTC 主链路资源隔离；不修改在跑 Session。

### 23.2 学生运行时平面（在线，实时）


**首次页面打开不建立 WebRTC。** 浏览器先显示 HTTP/CDN 的 `idle_frame`；学生开始录音时才 `ensure_media_session()`，回答结束后进入 Warm Idle，超过 `MEDIA_IDLE_TIMEOUT` 自动释放。

```text
学生端 Web
    │
    ├─ 录音上传
    │
    └─ WebRTC subscribe
    │
    ▼
学生端服务端
    │
    ├─ Local ASR
    ├─ Dify
    └─ TTS Scheduler
          │
          ├─ GPU0 CosyVoice
          └─ GPU1 CosyVoice
    │
    ▼
Session
    │
    ├─ 固定 avatar_version_id
    ├─ 加载 ready Avatar Package
    ├─ AvatarFrameController
    ├─ continuous FrameClock
    ├─ one Video Track
    └─ one Audio Track
    │
    ▼
LiveKit SFU
    │
    ▼
30+ students
```

### 23.3 关键隔离原则

```text
后台上传/处理形象
≠
修改正在运行的学生 Session
```

必须做到：

```text
新版本处理失败
→ 不影响旧 ready 版本

改默认形象
→ 只影响之后新建的 Session

运行中的 Session
→ 始终固定自己创建时的 avatar_version_id
```

禁止自动热替换当前正在使用的 Avatar Package。

如果未来确实需要“运行中切形象”，必须另做显式业务功能和切换协议，不属于首版。

## 24. 一句话开发约定

**学生端项目以 2 × RTX 4090 48GB 为本地语音计算资源；单班目标 30+ 独立 WebRTC Session；学生松开录音后由本地 Paraformer 做非流式多任务 ASR，识别文本交给 Dify，Dify 文本凑齐后进入双 GPU 本地 CosyVoice3 学生端 TTS（非流式整段合成）；每个学生端 Avatar 只有一个 AI 生成视频，上传后确定 `idle_frame / talk_start / talk_end`，学生端 Publisher 使用连续 25 FPS FrameClock 和同一个 LiveKit Video Track，在待机时重复 `idle_frame`、说话时循环 talking 区间，并通过程序 Crossfade 完成切换，从架构上禁止因待机/说话状态变化而切 MP4、seek 源视频时间轴或重建 WebRTC 视频轨。**

## 25. 最终验收红线

### WebRTC 空闲回收

- 页面打开但长期无操作时不得永久保持 WebRTC；
- 默认 `MEDIA_IDLE_TIMEOUT = 90s`；
- 超时后必须释放 Publisher、Audio/Video Track、LiveKit participant 与媒体缓冲；
- Business Session、Dify `conversation_id`、`avatar_version_id` 保留；
- 再次按下录音可自动重建 Media Session；
- 30+ 学生页面挂着但无人问答时，不应持续产生 30+ 路视频带宽。


以下任意一项不满足，项目不能按首版验收通过。

### 形象资产与运行时隔离

- 后台可在有学生在线时正常上传新 Avatar；
- 可在有学生在线时正常执行转码/帧分析；
- 新版本 `processing` 不可被 Session 使用，`ready` 后可供新建 Session；
- 改默认形象不得改变任何正在运行的 `session.avatar_version_id`；
- 新版本处理失败不得影响已有 ready 版本；
- 新建 Session 使用当前默认版本；
- 旧 Session 继续使用创建时锁定版本直到结束。

### WebRTC

- 可建立目标 **30+ 独立 Session**；
- Session 之间媒体和状态完全隔离；
- 单路断开/异常不影响其他路；
- 持续压测期间无系统性 Track 重建。

### 视频

```text
video_track_recreate_count = 0
video_pts_discontinuity_count = 0
```

并且：

- IDLE → TALKING 无明显黑屏/花屏；
- TALKING 循环无明显跳帧；
- TALKING → IDLE 无明显跳帧；
- interrupt 无明显跳帧；
- 禁止运行时切两个视频文件。

### ASR

- 多个完整录音可同时提交；
- 请求不串线；
- ASR Queue/Worker 正常工作；
- 30 路 burst 压测得到可接受的 P95；
- 单任务错误不影响其他任务。

### TTS

- GPU0/GPU1 均可承担 学生端 TTS Worker；
- 至少存在多个同时 active 的独立 TTS Job；
- Job 之间 PCM 不串线；
- 单 Job cancel 不影响其他 Job；
- 通过逐级并发压测得到真实 `MAX_TTS_ACTIVE_JOBS`；
- 生产上限必须保证 RTF、整段合成耗时和连续播放质量达标。
